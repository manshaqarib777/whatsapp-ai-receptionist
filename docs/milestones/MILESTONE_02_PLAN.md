## Objective

A tenant-aware authentication and authorization system that every later milestone
builds on. After this milestone the following are true and are not true now:

- A person can sign up, verify their email, sign in, and sign out.
- A forgotten password can be reset via a single-use, expiring, emailed link.
- A user can sign in without a password via a magic link.
- A user can enrol TOTP two-factor authentication and is challenged for it at sign-in.
- A user can sign in with Google or GitHub when those providers are configured.
- Every user belongs to at least one organization; users can belong to several and
  switch between them.
- Every request resolves to an authenticated user **and an active organization**, so
  `tenantId` can finally be derived server-side rather than assumed
  (`SECURITY_RULES.md` → Tenant Isolation).
- Roles and permissions are enforced **server-side** on every protected route.
- Security-relevant events are written to an append-only audit log.
- Unauthenticated access to a protected route redirects; unauthorised access is denied.

**Out of scope**: the inbox, dashboard, WhatsApp, AI, billing. No product features.

## Architecture Decisions

### ADR-0001 — Better Auth over Auth.js or a custom build

Written to `docs/architecture/decisions/ADR-0001-better-auth.md`.

**Context**: this milestone requires email/password, magic link, OAuth, TOTP 2FA,
organizations with roles, and session management. Session handling, TOTP verification,
and OAuth state validation are the highest-risk security surfaces in the product;
`SECURITY_RULES.md` treats a security defect as a stop condition.

**Decision**: Better Auth v1.6.25 with the `organization`, `twoFactor`, `magicLink`,
and `admin` plugins.

**Consequences**: far less hand-written security code; a schema partly generated by the
library; a meaningful dependency. Rejected: Auth.js v4 (no built-in 2FA, organizations,
or RBAC — most of this milestone would be hand-built anyway); a fully custom build
(highest risk in exactly the wrong place); Lucia (maintenance mode).

### Layering

Better Auth is an **infrastructure adapter**, not a domain layer. It is confined to
`src/lib/auth.ts` and `src/features/auth/`. The rest of the application depends on our
own `getSession()` / `requireSession()` / `requirePermission()` helpers, never on the
library directly. If the library is ever replaced, the blast radius is one feature
directory (`ARCHITECTURE_RULES.md` §13 — dependency inversion).

```
Route handler / Server Component
   → src/server/auth-context.ts      requireSession, requireOrg, requirePermission
      → src/lib/auth.ts              Better Auth instance (the only import site)
      → src/features/auth/services/  audit logging, permission resolution
         → repositories              Prisma
```

### RBAC model

Roles are **per-organization membership**, not global on the user — a person may be an
owner of one organization and a viewer of another.

| Role | Intent |
|---|---|
| `owner` | Full control including billing and deletion. Exactly one per org. |
| `admin` | Manage members, settings, and all data. |
| `member` | Day-to-day work: conversations, contacts, appointments. |
| `viewer` | Read-only. |

Permissions are explicit strings (`conversation:write`, `member:invite`,
`organization:delete`), mapped from roles by a single pure function so the mapping is
unit-testable without a database. **Checks are server-side only**; hiding a button is
not authorization (`SECURITY_RULES.md`).

### Session strategy

Database-backed sessions, not stateless JWTs. Rationale: revocation must be immediate —
"sign out all devices", a role change, or a compromised account cannot wait for a token
to expire. Cookies are `httpOnly`, `secure`, `sameSite=lax`, with a 30-day expiry and a
rolling 24-hour refresh.

The active organization is stored **on the session record**, not in a client-supplied
header or body field. This is what makes `tenantId` trustworthy.

## Database Impact

Substantial. Documented in `/docs/database/schema-change.md` before any migration.

**New tables** (Better Auth core + plugins, extended with our columns):

| Table | Purpose |
|---|---|
| `users` | Identity, email, verification state |
| `sessions` | Active sessions + `active_organization_id`, IP, user agent |
| `accounts` | Credential and OAuth provider links |
| `verifications` | Email verification, password reset, magic link tokens |
| `two_factors` | TOTP secret and backup codes |
| `organizations` | **The tenant.** Name, slug |
| `members` | User ↔ organization with `role` |
| `invitations` | Pending invites with expiry |
| `audit_logs` | Append-only security event log |

### The `tenant_id` question

`DATABASE_RULES.md` requires `tenant_id NOT NULL` on every table. That rule cannot
apply literally to the tables that *define* tenancy:

- `organizations` **is** the tenant — its own `id` is the tenant id.
- `users` are global; one person may belong to several organizations. Membership, not
  the user row, is tenant-scoped.
- `sessions`, `accounts`, `verifications`, `two_factors` hang off the user.
- `members` and `invitations` carry `organization_id` — these are the tenant-scoped
  join tables.

Every **business** table from Milestone 4 onward carries `organization_id NOT NULL`.
The exemption and its reasoning are recorded in the schema-change document so the
precedent is explicit rather than inferred.

### Audit log

Append-only, per `DATABASE_RULES.md`. No update or delete path exists in the
repository — not merely discouraged, absent. Columns: actor, organization, action,
entity, entity id, IP, user agent, metadata, timestamp. **No PII in metadata** —
ids only.

**Migration strategy**: `prisma migrate dev` locally, `prisma migrate deploy` in CI.
**Rollback**: documented per-table drop order in the schema-change document; no
production data exists yet.

## API Impact

Better Auth mounts its own handler; our routes wrap it or sit alongside it.

| Route | Method | Auth | Purpose |
|---|---|---|---|
| `/api/auth/[...all]` | GET, POST | mixed | Better Auth handler — sign in/up/out, callbacks, reset, magic link, 2FA |
| `/api/organizations` | GET | session | Organizations the user belongs to |
| `/api/organizations` | POST | session | Create an organization |
| `/api/organizations/active` | PATCH | session | Switch active organization |
| `/api/members` | GET | `member:read` | List members of the active org |
| `/api/members/:id` | PATCH | `member:update` | Change a member's role |
| `/api/members/:id` | DELETE | `member:remove` | Remove a member |
| `/api/invitations` | POST | `member:invite` | Invite by email |
| `/api/audit-logs` | GET | `audit:read` | Paginated audit log for the active org |

Every route uses `withApiHandler` from Milestone 1 and therefore inherits correlation
ids, structured logging, and the error envelope. Each satisfies all seven requirements
in `API_RULES.md`; documented in `/docs/api/auth.md` and `/docs/api/organizations.md`
before implementation.

**Middleware**: protected route groups redirect unauthenticated requests to `/login`
with a `next` parameter. Middleware performs an optimistic cookie check only — the
authoritative session check happens server-side in the layout, because middleware
cannot be trusted as the sole gate.

## Security Considerations

This is the milestone where `SECURITY_RULES.md` stops being aspirational.

| Area | Measure |
|---|---|
| Password storage | Library default (scrypt). Never hand-rolled. Minimum 12 characters, checked against a breach list where offline. |
| Session cookies | `httpOnly`, `secure`, `sameSite=lax`, signed, 30-day expiry, 24-hour rolling refresh |
| Session revocation | Immediate — database-backed. Sign-out-all invalidates every session row. |
| Session fixation | Session id regenerated on privilege change (sign-in, 2FA completion) |
| **Tenant isolation** | `organizationId` derived from the **session record**, never from a request body, query, or header. Every org-scoped query filters by it. Cross-tenant reads return 404. |
| Enumeration | Login, signup, and forgot-password return identical responses and timing whether or not the account exists. "No account with that email" is a data leak. |
| Rate limiting | Per-IP and per-identifier on sign-in, signup, reset, magic link, and 2FA. Redis is Milestone 24, so this milestone uses an in-process limiter — a **documented limitation**, not a silent gap. |
| Brute force | Progressive lockout after repeated failures, recorded in the audit log |
| Reset tokens | Single-use, 1-hour expiry, hashed at rest, invalidated on use and on password change |
| Magic links | Single-use, 15-minute expiry, invalidated on use |
| 2FA | TOTP with a 30s step and ±1 window; secrets encrypted at rest; 10 single-use backup codes shown exactly once |
| OAuth | State and PKCE verified by the library; providers disabled when unconfigured; email-verified claim required before linking to an existing account |
| Open redirect | The `next` parameter is validated as a relative path against an allow-list. An unvalidated redirect after login is a classic phishing vector. |
| Audit log | Append-only. Sign-in, sign-out, failed sign-in, password change, 2FA enrol/disable, role change, member removal, invitation. Actor, org, IP, user agent. **No PII in metadata.** |
| Logging | Never log passwords, tokens, secrets, or full email addresses. Redaction paths already configured in `src/lib/logger.ts`; extend for the new fields. |
| CSRF | `sameSite=lax` plus the library's origin check on state-changing requests |

## Testing Strategy

All four layers. Tests ship with the code (`TESTING_RULES.md`).

**Unit**
- Role → permission mapping: every role, every permission, including denials.
- `next` redirect validation: absolute URLs, protocol-relative (`//evil.com`),
  encoded traversal — all rejected.
- Password policy; audit-log payload construction (asserting no PII).

**Integration** (real Postgres)
- Sign up → verify → sign in → sign out, end to end.
- Reset token is single-use and expires; reuse fails.
- Magic link is single-use and expires.
- 2FA: enrolment, correct code, wrong code, replayed code, backup code, backup-code reuse.
- **Cross-tenant isolation**: a member of org A requesting org B's members receives 404.
- **`organizationId` from a request body is ignored** — the session value wins.
- Role change takes effect on the next request.
- Every protected route returns 401 unauthenticated and 403 without the permission.
- Audit rows are written for each security event; the repository exposes no update or
  delete.

**Component**
- Each auth form: loading, error, and success states; validation messages; disabled
  submit while pending; input preserved on failure.
- 2FA OTP input: keyboard entry, paste, backspace.
- Organization switcher.

**E2E**
- Full signup → onboarding → sign-in journey.
- Sign-out returns to `/login`; the back button does not restore the session.
- Unauthenticated access to a protected route redirects and returns after login.
- Keyboard-only completion of the login form.
- Both themes; RTL project.

**Coverage**: 90% on `src/features/auth/services` and `src/lib`, per `TESTING_RULES.md`.

## Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| 1 | **No email provider.** Verification, reset, magic link, and invitations all depend on delivery. | Certain | High | Define an `EmailPort` with a console adapter for development. Tests assert the port is called with the right payload, not that mail arrives. Flagged as the milestone's principal limitation; real provider needs credentials. |
| 2 | **No OAuth credentials.** Google/GitHub cannot be exercised end to end. | Certain | Medium | Providers configured from env and omitted when absent. Tests cover the configuration logic and the disabled path. Documented as unverified end to end. |
| 3 | Better Auth generates its own schema; it may not match `DATABASE_RULES.md` naming (snake_case, `created_at`). | High | Medium | Generate, then map explicitly with `@map`/`@@map` before the first migration. Review the generated schema rather than accepting it. |
| 4 | Rate limiting without Redis is per-process and resets on deploy. | Certain | Medium | In-process limiter now, documented limitation, replaced in M24. Better than none. |
| 5 | Tenant isolation bugs are silent and severe. | Medium | **Critical** | Isolation is proven by integration tests for every org-scoped route, not by inspection. A route without an isolation test does not ship. |
| 6 | Scope creep — auth naturally pulls in profile, billing, and settings UI. | High | High | Scope frozen to the PRD list. Anything else is logged in PROGRESS and deferred. |
| 7 | Auth pages built pre-design-system may need substantial rework in M3. | Medium | Low | Build with tokens and primitives only, no bespoke styling. Restyling then touches classNames, not structure. |
| 8 | Middleware treated as the security boundary. | Medium | High | Middleware is an optimistic redirect only. The authoritative check is server-side in the layout and in every route handler. A test asserts a protected API route rejects a request that bypasses middleware. |

  feature repositories. Route handlers call services; only repositories touch Prisma.

  acceptance route.
- Implement and test session listing and revocation in Security settings.
- Implement progressive failed-sign-in lockout and security-event audit coverage, or
  document a verified library-level control that satisfies the same acceptance test.
- Validate audit-log query input through a feature validator.

still belongs to Milestone 25. Those external-environment gates must remain explicit and
