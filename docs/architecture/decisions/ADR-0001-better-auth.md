# ADR-0001: Use Better Auth for authentication

Date: 2026-08-01
Status: Accepted
Milestone: 2

---

## Context

Milestone 2 requires, in one milestone: email/password sign-in, signup, forgotten and
reset password, TOTP two-factor authentication, magic links, OAuth, RBAC with
permissions, organizations, session management, and audit logging.

Three of those — session handling, TOTP verification, and OAuth state/PKCE validation —
are among the highest-risk security surfaces in any application. `SECURITY_RULES.md`
treats a security defect as a stop condition, and the project is explicitly a
production-grade multi-tenant SaaS rather than an MVP.

Neither the PRD nor `CLAUDE.md` specifies an authentication foundation, so a decision
is required before implementation.

The project also has a hard constraint that shapes this choice: `organizationId` must
be derivable **server-side from the session**, never from client input
(`SECURITY_RULES.md` → Tenant Isolation). Whatever we adopt must model organizations as
a first-class session concept, not as an afterthought bolted on above the auth layer.

---

## Decision

**Better Auth v1.6.25**, with the `organization`, `twoFactor`, `magicLink`, and `admin`
plugins, using the Prisma adapter and database-backed sessions.

Better Auth is confined to `src/lib/auth.ts` and `src/features/auth/`. The rest of the
application depends on our own `getSession()`, `requireSession()`, and
`requirePermission()` helpers — never on the library directly.

---

## Consequences

### What this makes easy

- The four plugins map almost exactly onto the milestone's requirement list, including
  organizations with per-membership roles and an active-organization concept stored on
  the session record — precisely what tenant isolation needs.
- Password hashing, TOTP, OAuth state and PKCE, and session cookies are handled by
  reviewed, maintained code rather than by us.
- Database-backed sessions give immediate revocation, which stateless JWTs cannot.

### What this makes hard

- A significant dependency in the most security-critical part of the system. Upgrades
  must be read, not applied blindly.
- Part of the schema is generated by the library and must be mapped to our naming
  conventions (`DATABASE_RULES.md`) rather than accepted as emitted. Risk 3 in the
  milestone plan.
- The library's abstractions must not leak into the domain. The wrapper layer is the
  mitigation, and it must be enforced in review.

### What we accept

If Better Auth is abandoned or proves unsuitable, replacement means rewriting
`src/lib/auth.ts` and `src/features/auth/`, plus a schema migration — a contained but
real cost. We accept that in exchange for not hand-writing security-critical
primitives.

---

## Alternatives Considered

### Auth.js (NextAuth) v4 — rejected

The most widely deployed option with strong OAuth support. Rejected because it provides
no built-in two-factor, organizations, or RBAC. Those are the majority of this
milestone's surface area, so we would hand-build exactly the parts we are trying to
avoid hand-building, while still carrying a dependency.

### Fully custom (`jose` + `@node-rs/argon2` + `otpauth` + `arctic`) — rejected

Maximum control and no framework lock-in; every line auditable. Rejected because it
places session handling, TOTP, and OAuth flows entirely on us. These are well-understood
problems with well-understood failure modes, and a subtle error in any of them is a
security incident rather than a bug. The control gained does not justify the risk taken.

### Lucia — rejected

Previously a good fit, but the project moved to maintenance mode and now positions
itself as a learning resource rather than a maintained library. Adopting it would mean
inheriting an unmaintained security dependency.

### Clerk / Auth0 / WorkOS (hosted) — rejected

Excellent products that would remove most of this milestone. Rejected because the PRD's
Milestone 22 requires an admin portal over tenants and users, Milestone 18 requires
multi-branch organizational structure, and Milestone 23 requires direct control of
security posture — all of which are harder when identity data lives in a third party.
Cost also scales per user in a product intended for SMB volume.
